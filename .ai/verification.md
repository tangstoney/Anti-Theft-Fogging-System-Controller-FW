## IMU（QMI8A01z）两条检测链路：本轮验证范围

参数全部在 [inc/project_config.h](../inc/project_config.h)，分“公共采样 / Any-Motion 唤醒 / 运动状态 / 疑似冲击 / 调试日志”五组，均为台架实验值。前一步不通过不进入下一步。

0. 接线与 ID：PB8=SCL、PB9=SDA（4.7k 上拉或模块自带），PC0 接 IMU INT1，3.3V 共地。复位后应看到 `IMU_OK addr=0x6A`；`FAULT imu_init=-2` 是 ID 不匹配（先查 0x6A/0x6B、SDA/SCL 是否接反），`-1` 是总线错误。
1. 采样链路自检（先确认数据是新的、连续的）：
   - 约每秒一行 `IMU_MOTION_STAT`；
   - `n` 稳定在 40~100（100Hz 采样、1 秒窗口；读取与芯片更新重叠时会丢弃整帧，`n` 低于 100 是正常的）；
   - `chip_n/1000` 接近 1000，明显偏小说明芯片实际 ODR 与配置不符或读取被阻塞；
   - `err=0`；`drop` 是丢弃帧数（aDA=0 或一致性复核不通过），静置时应接近 0；
   - `edges` 随扰动增加。
2. 停车静置：`rms` 只有噪声底（预期几十 mg），`state=STILL` 稳定；10 分钟内不出现 `SHOCK`，`VEHICLE_STATE` 不反复跳变。
3. 停车时轻敲/推晃模块（安全幅度）：应出现 `SHOCK ... peak_norm=...mg`，同时观察**下一次** `IMU_MOTION_STAT` 的 `state` 是否仍为 `STILL`——单次冲击不得直接把车辆判成行驶。若确实翻成 `MOVING`，先查 `RD91_MOTION_ENTER_WINDOWS` 是否被改小、冲击样本是否被计入（采样层在冲击事件期间不累加）。
4. 启动并行驶：从开始振动到 `VEHICLE_STATE v1=2` 的延迟应约为 `RD91_MOTION_ENTER_WINDOWS` 秒（当前 2 秒）。
5. 停车：从停稳到 `VEHICLE_STATE v1=1` 的延迟应约为 `RD91_MOTION_EXIT_WINDOWS` 秒（当前 3 秒）。
6. 正常路面接缝/减速带：记录运动状态是否被误判为 `MOVING`，以及 `SHOCK` 事件数量与峰值；这一项决定冲击阈值是否需要提高。
7. 台架抬升/倾斜/反复扰动：记录 `rms`、`SHOCK` 峰值与时长，为后续撬动检测（无大尖峰场景）留基线数据。

验收时同时记录两条链路是否互相干扰：冲击事件期间样本不计入运动统计，所以持续冲击会让窗口样本不足而判 `UNKNOWN`（不是 `STILL`），这是有意设计。

未上板验证项（不得在交付说明中写成已验证）：I2C 从机地址 0x6A/0x6B、400kHz 实际时序与上拉（传输层按厂商 I2C_Master 例程重写，仍须用逻辑分析仪确认 ACK/STOP/重复 START 波形）、PC0 有效电平与上升沿、Any-Motion 阈值字段宽度（手册 "5-bits fraction" 表述）、0.0625g/1样本的实际灵敏度、ODR 与滤波器实际效果、INT1 事件保持时间、10ms 采样对窄冲击峰值的漏采比例、一致性复核的实际丢弃率、全部振动/冲击阈值。

已知限制（本轮明确不解决）：
- 峰值是 10ms 采样点上的最大值，短于一个采样间隔的尖峰可能被漏掉，日志里看不到不代表没有发生；
- 芯片没有 FIFO 读取方案，没有高 g / 冲击专用引擎，Any-Motion 是相邻样本差值；
- `peak_norm` 是含重力的三轴合矢量，**不是**“冲击加速度本身”，不能直接换算成产品指标 0.5g/1.5g/150ms；
- 缓慢撬动/顶起没有大尖峰，疑似冲击链路按设计不会产生事件；
- 停车/行驶是振动推断，不是测速；低速匀速、坡道起步、单次开关车门都可能落在阈值附近。

阈值不是产品指标：`RD91_MOTION_*` 与 `RD91_SHOCK_*` 均未装车标定，本轮只是台架实验值。

## 本机声光报警（台架）：本轮验证范围

配置在 [inc/project_config.h](../inc/project_config.h) 第 5 组。判定以“期望状态 → 日志 → 实测波形/声音/灯”为准；日志只证明 MCU 侧动作，不能证明芯片真的播放了报警内容。

0. 接线与上电默认态：PB0=CLK、PB1=DATA、PA1=BUSY、PA2=蜂鸣器驱动、PA3/PA4 红/蓝；上电三路必须全灭无声，CLK/DATA 为低。WT 按 3.3V 供电（若 5V 必须加电平转换），IO2 不得外接上拉。
1. 初始化：复位后应有 `WT_READY wire=2WIRE addr_mode=SINGLE seg=1 busy=1`。`FAULT wt_init=-1` 表示 DWT 周期计数器不可用，此时驱动拒绝发码。
2. 启动：按 PA0 或调试器调用 `Bench_AlarmSelfTest(1)`。日志顺序应为 `BENCH_ALARM_SELFTEST on=1` → `ALARM_OUT_BUZZER on=1` → `ALARM_OUT_LAMP blink=1 period_ms=250` → `ALARM_VOICE_CMD seg=1` → `ALARM_VOICE_PLAYING seg=1`。现象：蜂鸣器常响，红/蓝每 250ms 交替，语音段循环。
3. 停止：再按一次或调用 `Bench_AlarmSelfTest(0)`，应出现 `ALARM_OUT_BUZZER on=0`、`ALARM_OUT_LAMP blink=0`、`ALARM_OUT_STOP stop_us=... worst_us=...`，三路立即关闭。记录 `stop_us` 作为实测停止延迟。
4. 幂等：连续两次启动不应重复打印 `ALARM_VOICE_CMD`（芯片保持当前播放）；连续两次停止不应重复发 FE（只应有一条 `ALARM_OUT_STOP`）。
5. 快速切换：启动后立刻停止、再快速交替 10 次，最终现象必须等于最后一次请求（最后是停止则全灭）。不得出现停止后仍在响/闪，或启动后灯停在单色不动。
6. 语音模块缺失：拔掉 WT（BUSY 靠 MCU 上拉读到高），启动后约 100ms 内应出现 `FAULT alarm_voice op=busy err=-3`；蜂鸣器与灯仍要正常启动/停止，不能出现“正在播放”的假日志。
7. BUSY 未接入：把 `RD91_WT_BUSY_ENABLED` 置 0 重编译，日志应为 `ALARM_VOICE_CMD_SENT busy=DISABLED`，停止时仍发 FE。
8. 系统时间不被阻塞：报警期间 `HEARTBEAT` 与 `IMU_MOTION_STAT` 持续出现，`chip_n/1000` 不明显下降；停止后 tick 与采样立即恢复。
9. 逻辑分析仪：按 README“逻辑分析仪核对步骤”核对 CLK 高5ms/低5ms、8 位 LSB 先发、700µs 位周期、地址后跟 F2、停止只有 FE、命令间隔≥2ms；量测连续 8 位期间（约5.6ms）的中断响应，确认 SysTick/UART 中断仍被服务。

未上板验证项（不得写成已验证）：到手 WT 模块烧录的控制方式（一线/两线）、段数与单/双字节地址格式、报警段号的实际内容、音量命令是否被接受、BUSY 极性/电平/变化时间、3.3V 下两线时序兼容性、蜂鸣器驱动级与声压是否满足产品指标、双色灯是 3 脚共阴/共阳还是 2 脚反并联、250ms 闪烁是否为产品要求、DWT CYCCNT 在该板的可用性与精度、锁调度 5.6ms 对 100Hz 采样的实际影响、实测停止延迟上限。

已知限制：BUSY 只能证明“芯片在播放”，不能确认内容就是报警段；BUSY 超时只说明未观察到播放，不能反证命令没收到；蜂鸣器/灯记录的是已驱动电平，不是声压/光强确认；首次启动需发地址+F2 两条命令（约 35ms），期间业务层的停止请求在每条命令后检查；期望状态变化统一有最多 1 tick（10ms）的合并延迟，已包含在 `stop_us` 内。

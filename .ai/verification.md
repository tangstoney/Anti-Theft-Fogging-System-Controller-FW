## IMU（QMI8A01z）两条检测链路：本轮验证范围

参数全部在 [inc/project_config.h](../inc/project_config.h)，分“公共采样 / Any-Motion 唤醒 / 运动状态 / 疑似冲击 / 调试日志”五组，均为台架实验值。前一步不通过不进入下一步。

0. 接线与 ID：PB8=SCL、PB9=SDA（4.7k 上拉或模块自带），PC0 接 IMU INT1，3.3V 共地。复位后应看到 `IMU_OK addr=0x6A`；`FAULT imu_init=-2` 是 ID 不匹配（先查 0x6A/0x6B、SDA/SCL 是否接反），`-1` 是总线错误。
1. 采样链路自检（先确认数据是新的、连续的）：
   - 约每秒一行 `IMU_MOTION_STAT`；
   - `n` 稳定在 40~100（100Hz 采样、1 秒窗口；读取与芯片更新重叠时会丢弃整帧，`n` 低于 100 是正常的）；
   - `chip_n/1000` 接近 1000，明显偏小说明芯片实际 ODR 与配置不符或读取被阻塞；
   - `err=0`；`drop` 是丢弃帧数（aDA=0 或一致性复核不通过），静置时应接近 0；
   - `edges` 随扰动增加。
2. 停车静置：`rms` 只有噪声底（预期几十 mg），`state=STILL` 稳定；10 分钟内不出现 `SHOCK`，`VEHICLE_STATE` 不反复跳变。
3. 停车时轻敲/推晃模块（安全幅度）：应出现 `SHOCK ... peak_norm=...mg`，同时观察**下一次** `IMU_MOTION_STAT` 的 `state` 是否仍为 `STILL`——单次冲击不得直接把车辆判成行驶。若确实翻成 `MOVING`，先查 `RD91_MOTION_ENTER_WINDOWS` 是否被改小、冲击样本是否被计入（采样层在冲击事件期间不累加）。
4. 启动并行驶：从开始振动到 `VEHICLE_STATE v1=2` 的延迟应约为 `RD91_MOTION_ENTER_WINDOWS` 秒（当前 2 秒）。
5. 停车：从停稳到 `VEHICLE_STATE v1=1` 的延迟应约为 `RD91_MOTION_EXIT_WINDOWS` 秒（当前 3 秒）。
6. 正常路面接缝/减速带：记录运动状态是否被误判为 `MOVING`，以及 `SHOCK` 事件数量与峰值；这一项决定冲击阈值是否需要提高。
7. 台架抬升/倾斜/反复扰动：记录 `rms`、`SHOCK` 峰值与时长，为后续撬动检测（无大尖峰场景）留基线数据。

验收时同时记录两条链路是否互相干扰：冲击事件期间样本不计入运动统计，所以持续冲击会让窗口样本不足而判 `UNKNOWN`（不是 `STILL`），这是有意设计。

未上板验证项（不得在交付说明中写成已验证）：I2C 从机地址 0x6A/0x6B、400kHz 实际时序与上拉（传输层按厂商 I2C_Master 例程重写，仍须用逻辑分析仪确认 ACK/STOP/重复 START 波形）、PC0 有效电平与上升沿、Any-Motion 阈值字段宽度（手册 "5-bits fraction" 表述）、0.0625g/1样本的实际灵敏度、ODR 与滤波器实际效果、INT1 事件保持时间、10ms 采样对窄冲击峰值的漏采比例、一致性复核的实际丢弃率、全部振动/冲击阈值。

已知限制（本轮明确不解决）：
- 峰值是 10ms 采样点上的最大值，短于一个采样间隔的尖峰可能被漏掉，日志里看不到不代表没有发生；
- 芯片没有 FIFO 读取方案，没有高 g / 冲击专用引擎，Any-Motion 是相邻样本差值；
- `peak_norm` 是含重力的三轴合矢量，**不是**“冲击加速度本身”，不能直接换算成产品指标 0.5g/1.5g/150ms；
- 缓慢撬动/顶起没有大尖峰，疑似冲击链路按设计不会产生事件；
- 停车/行驶是振动推断，不是测速；低速匀速、坡道起步、单次开关车门都可能落在阈值附近。

阈值不是产品指标：`RD91_MOTION_*` 与 `RD91_SHOCK_*` 均未装车标定，本轮只是台架实验值。

## 本机声光报警（台架）：本轮验证范围

配置在 [inc/project_config.h](../inc/project_config.h) 第 5 组。判定以“期望状态 → 日志 → 实测波形/声音/灯”为准；日志只证明 MCU 侧动作，不能证明芯片真的播放了报警内容。

0. 接线与上电默认态：PB0=单线 DATA（芯片 IO2）、PA1=BUSY、PA2=蜂鸣器驱动、PA3/PA4 红/蓝；PB1（芯片 IO3）单线模式不接、保持低。上电三路必须全灭无声，数据线为低。WT 按 3.3V 供电（若 5V 必须加电平转换），IO2 不得外接上拉。
1. 初始化：复位后应有 `WT_READY wire=1WIRE addr_mode=SINGLE seg=1 busy=1`。`FAULT wt_init=-1` 表示 DWT 周期计数器不可用，此时驱动拒绝发码。
2. 启动：按 PA0 或调试器调用 `Bench_AlarmSelfTest(1)`。日志顺序应为 `BENCH_ALARM_SELFTEST on=1` → `ALARM_OUT_BUZZER on=1` → `ALARM_OUT_LAMP blink=1 period_ms=250` → `ALARM_VOICE_CMD seg=1` → `ALARM_VOICE_PLAYING seg=1`。现象：蜂鸣器常响，红/蓝每 250ms 交替，语音段循环。
3. 停止：再按一次或调用 `Bench_AlarmSelfTest(0)`，应出现 `ALARM_OUT_BUZZER on=0`、`ALARM_OUT_LAMP blink=0`、`ALARM_OUT_STOP stop_us=... worst_us=...`，三路立即关闭。记录 `stop_us` 作为实测停止延迟。
4. 幂等：连续两次启动不应重复打印 `ALARM_VOICE_CMD`（芯片保持当前播放）；连续两次停止不应重复发 FE（只应有一条 `ALARM_OUT_STOP`）。
5. 快速切换：启动后立刻停止、再快速交替 10 次，最终现象必须等于最后一次请求（最后是停止则全灭）。不得出现停止后仍在响/闪，或启动后灯停在单色不动。
6. 语音模块缺失：拔掉 WT（BUSY 靠 MCU 上拉读到高），启动后约 100ms 内应出现 `FAULT alarm_voice op=busy err=-3`；蜂鸣器与灯仍要正常启动/停止，不能出现“正在播放”的假日志。
7. BUSY 未接入：把 `RD91_WT_BUSY_ENABLED` 置 0 重编译，日志应为 `ALARM_VOICE_CMD_SENT busy=DISABLED`，停止时仍发 FE。
8. 系统时间不被阻塞：报警期间 `HEARTBEAT` 与 `IMU_MOTION_STAT` 持续出现，`chip_n/1000` 不明显下降；停止后 tick 与采样立即恢复。
9. 逻辑分析仪（单线）：按 README“逻辑分析仪核对步骤”核对数据线先高 5ms/低 5ms、每 bit 高在前低在后（600/200 为 1、200/600 为 0，LSB 先发）、地址后跟 F2、停止只有 FE、命令间隔≥2ms；量测连续 8 位期间（约 6.4ms）的中断响应，确认 SysTick/UART 中断仍被服务。需要验证两线路径时把 `RD91_WT_WIRE_MODE` 改 2、重新接线另测，不能把单线结果当成两线已验证。

未上板验证项（不得写成已验证）：到手 WT 模块烧录的控制方式（硬件按单线，须确认模块确为单线工程）、段数与单/双字节地址格式、报警段号的实际内容、音量命令是否被接受、BUSY 极性/电平/变化时间、3.3V 下单线时序兼容性、蜂鸣器驱动级与声压是否满足产品指标、双色灯是 3 脚共阴/共阳还是 2 脚反并联、250ms 闪烁是否为产品要求、DWT CYCCNT 在该板的可用性与精度、锁调度 6.4ms 对 100Hz 采样的实际影响、实测停止延迟上限。

已知限制：BUSY 只能证明“芯片在播放”，不能确认内容就是报警段；BUSY 超时只说明未观察到播放，不能反证命令没收到；蜂鸣器/灯记录的是已驱动电平，不是声压/光强确认；首次启动需发地址+F2 两条命令（单线每字节约 18.4ms，合计约 37ms），期间业务层的停止请求在每条命令后检查；期望状态变化统一有最多 1 tick（10ms）的合并延迟，已包含在 `stop_us` 内。

## 充电/状态指示灯（台架）：本轮验证范围

配置在 [inc/project_config.h](../inc/project_config.h) 第 6 组。判定以“寄存器状态 → 日志 → 灯色”为准；日志只证明 MCU 侧判定与 GPIO 电平，不能证明真实充电电流/电量。前一步不通过不进入下一步。

0. 接线与上电默认态：PA5=红、PA6=绿，按 `RD91_CHG_LED_WIRING` 接线（默认 3 脚共阴高有效）；SGM41513 的 SCL/SDA 接 PB8/PB9（与 IMU 共用 I2C1，0x1A）。上电到 `ChargeLed_Init()` 执行前两灯必须全灭。
1. 初始化：复位后应有 `SGM_READY addr=0x1A pn=0 rev=... poll_ms=500`。`FAULT sgm_probe=NO_ACK` 先查 0x1A 地址、上拉、供电与接线；探测失败不得影响 IMU、按键、声光等其他功能。
2. 无输入：不接充电电源时，约 1 秒内出现 `CHARGE_STATE state=NO_INPUT`，两灯全灭。
3. 充电中：插入充电电源，`CHARGE_STATE state=CHARGING`，红灯常亮；充电电流是芯片自主行为，不由本固件控制。
4. 充满：电池充满后 `CHARGE_STATE state=FULL`，绿灯常亮。
5. 故障提示：先把 `RD91_BENCH_CHG_SELFTEST` 置 1 重新编译（默认 0 时符号不生成），调试器调用 `Bench_ChargeSimSet(3)`，应出现 `CHARGE_STATE state=FAULT chrg=2 bat=0 ntc=0 reg08=0x?? reg09=0x??`，红灯 500ms 亮/灭交替；`Bench_ChargeSimSet(1)` 回到充电中，红灯常亮。
6. 台架模拟全表：依次 `Bench_ChargeSimSet(0/1/2/3/4)` 再回 `-1`，灯色分别应为 灭/红/绿/红闪/灭/按真实 I2C；每次切换在 500ms 采样 + 500ms 去抖后稳定，不得来回闪。验证完把宏改回 0 重新编译，确认镜像尺寸回落、`Bench_ChargeSimSet` 符号消失。
7. 去抖：反复插拔或用模拟值快速切换，原始状态不保持 500ms 时灯色不应跟随抖动。
8. 总线共享：充电轮询运行期间 `IMU_MOTION_STAT` 持续输出，`err`、`drop` 不明显上升，`chip_n/1000` 不明显下降；这一步验证 I2C 互斥锁没有让 IMU 采样变慢或丢失事务。
9. 运行中摘掉充电器：读失败只出现一次 `FAULT sgm_read=NO_ACK addr=0x1A`，灯保持熄灭（UNKNOWN 不能当成“无输入”或“充满”）；恢复后出现 `SGM_RECOVERED` 并继续正常指示。

未上板验证项（不得写成已验证）：SGM41513 实际从机地址与 PN/DEV_REV 解码、REG08/REG09 各字段定义与“REG09 连续读两次取当前故障”的实际行为、充电器在到手板上是否上电且挂在该总线上、PA5/PA6 是否引出、双色灯是 3 脚共阴/共阳还是 2 脚反并联、PA5/PA6 是否与板上其他功能冲突、真实插拔/预充/快充/充满时的寄存器序列与延迟、I2C 互斥锁对 IMU 采样节奏的实际影响。

已知限制：状态来自充电器寄存器，不是 CW2217 电量；本固件不计算剩余电量、不控制充电电流/截止电压；不写任何寄存器，充电器保持默认自主模式，看门狗故障位被刻意忽略（不是充电故障）；无输入/禁用/故障三种状态的颜色与 500ms 闪烁是台架取值，产品只确认了“充电中红色、充满绿色”；故障位经 REG09 历史锁存，第一次读清历史、第二次读取当前，两次之间若状态变化会在下一轮修正；去抖使状态变化最多延迟约 1 秒。

## 电池电量（CW2217，台架）：本轮验证范围

配置在 [inc/project_config.h](../inc/project_config.h) 第 7 组。判定以“寄存器原始值 → 换算 → 事件 → 业务日志”为准；日志只证明 MCU 侧读数，不能证明电池实际容量或续航。前一步不通过不进入下一步。

0. 接线与上电：CW2217 的 SCL/SDA 接 PB8/PB9（与 IMU、SGM41513 共用 I2C1，0x64），VCELL/VDD/TS/CSP/CSN 按原理图接电池侧；上电后即由固件初始化，不依赖按键。
1. 初始化：复位后应有 `BATT_READY addr=0x64 version=0xA0 poll_ms=2000`。`FAULT cw2217_probe=-1` 查总线/供电/接线；`-3 version=0x??` 说明地址有应答但不是 CW2217；`FAULT cw2217_wake=...` 说明 CONFIG 写入失败。任何失败都不得影响 IMU、按键、声光与充电指示灯。
2. 首次读数：约 2 秒内出现 `BATTERY_STAT src=I2C percent=... valid=1 chg=... soc_raw=... mv=... t=...`；`soc_raw/256` 应与 `percent` 相差不超过 1；`mv` 与万用表测得的单节电池电压一致（312.5µV/LSB）；`t` 与 NTC 实际温度量级一致（未接 NTC 时不得把该值当作有效温度）。
3. 充电标志：插入充电器且指示灯为红时 `chg=1`；充满（绿灯）时为 `chg=0`；无输入/禁用为 0；充电器状态未知或故障时为 0xFF（对应业务 `charging_valid=0`）。`chg` 来自充电器而不是电量计，不得据此宣称电池正在充电。
4. 电量变化：放电过程中 `percent` 应逐步下降、充电时逐步上升；记录 1% 变化所需时间，与整机负载一起作为后续低电策略的基线。FastCali 可能调整读数，偶发 1~2% 回调属正常，持续跳变需记录。
5. 台架模拟：把 `RD91_BENCH_BATT_SELFTEST` 置 1 重新编译后 `Bench_BatterySimSet(50)` → `BATTERY_STAT src=SIM percent=50` 与 `BATTERY_REPORT`；依次 0/25/50/75/100 检查事件与业务 `BATTERY` 日志；`Bench_BatterySimSet(-1)` 回到真实 I2C。验证完把宏改回 0 重新编译。
6. 过期处理：拔掉电量计（或保持 -1 但无硬件）后，单次读取失败只打印一次 `FAULT cw2217_read=NO_ACK`，6 秒内显示仍保留上次有效值，随后出现一次 `BATTERY_REPORT ... valid=0`；恢复后打印 `CW2217_RECOVERED` 并重新上报有效百分比。全程不得把失败当成 0%。
7. 总线共享：电量轮询与充电轮询同时运行时，`IMU_MOTION_STAT` 持续输出，`err`/`drop` 不明显上升；三个器件的事务不交错（可用逻辑分析仪抽查一条 SOC 读事务的完整性）。
8. 写操作核对：逻辑分析仪只看初始化阶段的 `0x08=0x30`、`0x08=0x00` 两次写；运行期间不得再出现任何写事务（本工程不写 CONFIG/INT_CONF/T_HOST）。
9. 重启行为：复位 MCU（电量计保持供电）后重新执行唤醒序列，记录 SOC 是否重新估计、与复位前的差值；手册说明 restart 会重新计算 SOC。

未上板验证项（不得写成已验证）：CW2217 实际地址 0x64 与 VERSION=0xA0、CONFIG 0x30/0x00 唤醒序列的实际效果、唤醒后首次 SOC 的建立时间、SOC/VCELL/TEMP 的量程/精度与手册换算一致、SOC 高低字节分两次读取的实际一致性、电量计是否在到手板上上电及电池侧接线、6s 过期与 2s 采样是否为合适取值、`chg` 由充电器状态推导是否符合产品显示要求。

已知限制：SOC 是电量计算法的估计值，不是库仑计实测容量；本固件不读电流、不配置电池 profile、不处理 NTC 类型（温度仅记录）；低电阈值/告警动作/跨重启持久化未实现（Q11）；初始化写 CONFIG 会重启电量计算，复位后首次读数可能略有不同；读取失败在 6 秒内继续显示上次值，这期间显示不是“当前事实”，只能算“最近已知值”。
